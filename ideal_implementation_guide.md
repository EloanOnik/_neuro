# Архитектурный гайд и пошаговый план идеальной реализации «Нейростримерши»

Этот документ — детальный технический разбор и руководство по проектированию автономного AI-стримера с нуля. Здесь описано, как построить надежную, легко поддерживаемую и масштабируемую систему, избегая типичных архитектурных грабель.

---

## 1. Философия и принципы разработки AI-стримеров

Стриминг в реальном времени — это **асинхронная система реального времени (Real-Time System)**. В отличие от обычных чат-ботов или REST API, здесь критичны три вещи:
1. **Латентность (Задержка):** Зритель не должен ждать ответ по 15 секунд. От получения сообщения до звука в OBS должно проходить не более 3–5 секунд.
2. **Непрерывность и Потоковость (Streaming):** LLM должна генерировать токены на лету, а TTS должен озвучивать предложения по мере их формирования, а не ждать окончания всего ответа.
3. **Устойчивость к сбоям (Resilience):** Если упал Twitch-чат или зависла Ollama, бот не должен падать с `Crash`. Он должен залогировать ошибку, попытаться переподключиться и продолжить работу.

## 2. Идеальная архитектура (Чистая структура)

Мы отходим от громоздких акторных систем в пользу **модульной асинхронной архитектуры на базе очередей (`asyncio.Queue`)**.

```
architecture/
├── config/                 # Pydantic настройки и YAML файлы
│   ├── settings.py         # Загрузчик конфигурации (pydantic-settings)
│   ├── system.yaml         # Промпт, личность, эмоции
│   └── voices.yaml         # Настройки голосов и пресетов
├── core/                   # Низкоуровневые движки (чистая логика)
│   ├── llm.py              # Ollama клиент (stream, async)
│   ├── tts.py              # Kokoro/Edge-TTS клиент + SoundDevice
│   ├── stt.py              # Faster-whisper + PTT
│   └── memory.py           # ChromaDB + bge-m3 (RAG)
├── adapters/               # Внешние интерфейсы (IO, API)
│   ├── chat/
│   │   ├── base.py         # Абстрактный класс ChatAdapter
│   │   └── twitch_io.py    # Асинхронный Twitch клиент (TwitchIO)
│   └── obs/
│       └── obs_ws.py       # Управление OBS через WebSocket
├── services/               # Бизнес-логика и оркестрация
│   ├── brain.py            # LLM + Context + Buffer (оркестрация реплик)
│   ├── tts_player.py       # Приоритетная очередь озвучки
│   ├── moderation.py       # Фильтрация мата, спама, стоп-слов
│   └── trigger_engine.py   # Обработка донатов, сабов, таймеров
├── pipeline/
│   └── stream_loop.py      # Главный координирующий цикл (Event Loop)
└── main.py                 # Точка входа, инициализация, graceful shutdown
```

## 3. Пошаговый план идеальной реализации (Как бы писал я)

### Шаг 1: Конфигурация (`config/settings.py`)
Никаких захардкоженных токенов, путей и портов. Используем `pydantic-settings` с валидацией через YAML.
- Читаем `system.yaml` при старте.
- Проверяем наличие моделей в директории `tts_models/`.

### Шаг 2: Аудиоподсистема и автопоиск VB-Cable (`core/tts.py`)
Никаких жестких индексов устройств (`device_index=13`). При старте система должна сканировать аудиоустройства через `sounddevice`:
```python
import sounddevice as sd

def find_virtual_cable():
    devices = sd.query_devices()
    for idx, dev in enumerate(devices):
        if "CABLE Input" in dev["name"] and dev["max_output_channels"] > 0:
            return idx
    raise RuntimeError("VB-Cable не найден! Установите виртуальный кабель.")
```

### Шаг 3: Мозг и потоковая буферизация (`services/brain.py`)
Ключевая задача Brain — превратить поток токенов от Ollama в осмысленные предложения для TTS без пауз:
1. Принимаем сообщение из очереди чата.
2. Добавляем в `ChatContext`.
3. Запрашиваем Ollama через `stream_ask_generator`.
4. Накапливаем токены в буфере `buffer += token`.
5. Как только `buffer` заканчивается на знак препинания (`.`, `!`, `?`), мгновенно отправляем его в `TTSPlayer.speak(sentence)`, очищая буфер.

### Шаг 4: Асинхронный чат (`adapters/chat/`)
Забываем про блокирующие сокеты и потоки (`threading`), если они не нужны. Для Twitch идеально использовать асинхронную библиотеку `TwitchIO` или обернуть IRC в полноценный `asyncio.Protocol`. Это избавит от конфликтов с GIL и проблем с остановкой потоков.

### Шаг 5: Graceful Shutdown (Критически важно!)
В `main.py` обязательно настраиваем перехват сигналов завершения (`SIGINT`, `SIGTERM`), чтобы при нажатии `Ctrl+C`:
1. Останавливался чат.
2. Очищалась очередь TTS и закрывался аудиопоток.
3. Отправлялся запрос выгрузки модели в Ollama (`keep_alive: 0`), освобождая VRAM видеокарты.
4. Закрывались все HTTP-клиенты.

## 4. Советы новичку в разработке AI-систем и стримеров

### 1. Не усложняйте архитектуру на старте (Avoid Over-engineering)
Многие новички пытаются сразу прикрутить микросервисы, Docker Compose на 10 контейнеров, Kafka, RabbitMQ, графовые базы данных и сложные акторные модели. 
> *Реальность:* Для работающего MVP вам нужен один монолитный Python-процесс на `asyncio`. Этого хватит с головой на первые полгода стримов.

### 2. Всегда обрабатывайте блокирующий код через `asyncio.to_thread`
Если ваша библиотека (например, `sounddevice` при открытии стрима, или тяжелый вызов чата, или чтение файла) делает блокирующие вызовы (`blocking I/O`), это мгновенно заморозит весь event loop, и бот перестанет реагировать на что-либо. Оборачивайте такое в `await asyncio.to_thread(...)`.

### 3. Логируйте всё с помощью `loguru`
Забудьте про `print()`. На стриме у вас будут десятки событий в секунду: сообщения чата, токены LLM, таймкоды TTS, ошибки соединения. 
Используйте `loguru` с цветным выводом в консоль и одновременной записью в файловый лог с ротацией (`logger.add("logs/stream.log", rotation="10 MB")`). Это сэкономит вам сотни часов при дебаге.

### 4. Тестируйте компоненты изолированно (Unit-тесты для себя)
Не пытайтесь запустить всё сразу (`Twitch -> LLM -> TTS`). 
- Сначала запустите скрипт, который проигрывает одно слово в VB-Cable.
- Затем скрипт, который делает запрос к Ollama и выводит текст.
- Затем проверьте чтение чата.
Только убедившись, что каждый кирпичик работает по отдельности, собирайте их в единый пайплайн.

### 5. Помните про «галлюцинации» промптов и контекста
LLM в режиме стрима любит уходить в бесконечные рассуждения или отвечать портяночным текстом на 5 абзацев. 
- Жестко ограничивайте `max_tokens` (например, 60–80 токенов).
- В системном промпте явно прописывайте: *«Отвечай кратко, 1-2 предложения, в разговорном стиле»*. Промпт-инженерия решает 80% проблем с поведением бота.
